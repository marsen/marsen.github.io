[實作筆記] 一句追問就露餡：AI 祕書為什麼需要 Session 記憶

前情提要

AIris 的溝通管道是 LINE，架構分兩條路：L1 是每天早上 09:00 主動推播的晨間簡報（cron 觸發，單向），L2 是 LINE webhook 收訊息、雙向對話，靠 create_record、query_records 兩個自訂 tool 讀寫 Notion 記憶。

今天實測 L2，問她「列出本日的待辦」，答得不錯——查了 Notion，列出跟進事項跟 PBI，還主動說日曆行程跟待回信件她讀不到，需要授權。我順口追問「怎麼授權」，結果她完全不記得自己剛剛講了什麼，答非所問,開始從人格手冊裡亂猜，扯到跟社交推進沾不上邊的授權範圍。

這篇記錄這個坑是怎麼回事，跟後來怎麼想清楚該補的東西。

露餡的過程

對話大概長這樣：

第二句「怎麼授權」單獨拿出來看，任何人都看得出來是在接續上一句的「要不要授權」。但 AIris 接不住，因為她根本不知道自己剛剛問了什麼。

根本原因：每則訊息都是一次全新的呼叫

翻了 ProcessIncomingMessageUseCase（L2 的核心 use case），問題很直白：每一則進來的 LINE 訊息，都是獨立組一次 prompt、獨立呼叫一次 LLM，呼叫之間沒有任何上一輪的記憶被帶進去。「怎麼授權」這句話送進去的時候，LLM 看到的世界裡根本沒有「剛剛問過要不要授權」這件事,只能憑人格手冊亂猜。

翻舊的技術設計文件，其實當初有寫到「對話記憶：短期用記憶體或 Redis 快取留 10 輪，長期一律落地 Notion」。但 L2 開發階段,先把 create_record/query_records 兩個 tool 跑通就把這塊跳過了，變成技術債留到現在才現形。

所以這不是一個 bug，是設計時就知道要做、但先延後的功能，剛好被一次真實追問戳破。

換個角度想：真人祕書會怎麼做

如果 AIris 是一個真人祕書，早上問你「你昨天說要放棄那個專案，還算數嗎？」，你回「對，維持」，她完全不需要什麼特殊機制去理解你在回答什麼——因為這就是同一段對話的下一句，她自己記得 30 秒前問了什麼。

會卡住,不是因為「聽懂追問」這件事本身多難做，是因為在目前的架構裡，L1（推播）跟 L2（對話）是兩條完全不相干的路，中間沒有共用記憶。這個問題在真人祕書身上根本不存在，因為她的「問」跟「聽你回答」本來就是同一場對話——L1 和 L2 這種技術上的分層，在真人身上是不存在的區分，是我自己的架構切出來的邊界，不是對話本質上該有的邊界。

業界怎麼做：Session/Thread 是標準做法

換個角度查證，業界對話型 AI 產品的做法很一致：

  1. Session/Thread 模型——ChatGPT、Claude.ai 這類產品，都是維護一個「對話串」，每一輪把新訊息接上去，模型看到的是完整（或有裁剪）的歷史，不是每次從零開始。這不是什麼進階技巧，是對話型產品的地基。

  2. 手上剛好有現成工具：Claude Agent SDK 本身就有 resume/session ID 機制，session 由 SDK 自己在背後保存（存在 ~/.claude/projects/<sanitized-cwd>/... 這類路徑），不用自己刻訊息歷史的存取跟裁剪邏輯。AIris 只服務我一個人（白名單機制鎖定），甚至不用管理「多個 session」——一組固定的 session id，每次都 resume 同一個就好，比自己維護一份訊息陣列還簡單。

  3. 短期記憶 + 長期記憶分開，是 AI 陪伴類產品常見的架構：短期是最近幾輪對話的原始內容，長期是抽取出來、結構化的事實。這正好跟 AIris 現有架構吻合——長期那塊（Notion + create_record/query_records）已經有了，短期那塊目前是空的，剛好對上原始 SPEC 寫的「短期用快取、長期落 Notion」。

  4. 額外一提，跟核心問題無關但值得記著：LINE 有個「loading 動畫」API，訊息處理中可以先顯示打字中的動畫，讓一次要等 15~25 秒的等待不會感覺像沒反應。這是體驗加分，不是這次要解的問題，先記一筆。

結論：先補 Session，確認機制自然就有了

原本想直接做「確認待處理決定」這種功能——AIris 記得自己問過「要不要授權」，下一句能對得上。但這其實是「對話連貫」這個更基礎能力底下的其中一種情境而已。如果只挑這個情境做，等於是在發明一套專用機制去判斷「這句話在回答哪件事」，下次換一個情境（比如追問「剛剛列的第二件事是什麼」）又要重做一次。

順序反過來排：先做 session 續接，用 Agent SDK 內建的 resume 機制，把 LINE userId 對應到一個固定的 session id。地基打好之後，「確認待處理決定」這類需要上下文的功能，會是這個能力底下自然長出來的行為，不用另外設計。

小結

這次踩的坑，說穿了是把「多輪對話」跟「單次問答」混在一起用同一套機制在做。L1 是單向推播，本來就不需要記憶；L2 是雙向對話，卻被當成跟 L1 一樣的無狀態呼叫在寫，一個追問就露餡。

真人祕書的思路和業界標準做法在這裡指向同一個方向：對話本身要先連貫，其他建立在「記得上一句」之上的功能才有地方長。先補 session，再回頭做確認機制，順序不能反。

(fin)
